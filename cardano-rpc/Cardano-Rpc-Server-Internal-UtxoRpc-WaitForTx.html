Handle the WaitForTx SubmitService RPC method.

Reports STAGE_MEMPOOL when a ref enters the mempool and STAGE_CONFIRMED when a ref appears in a block applied after the stream opened, and closes the stream once every ref has reached STAGE_CONFIRMED.

Threading model: one thread per call, with no shared state. Each step is one STM wait on the chain tip and the pending refs' mempool membership, bounded by timeout; on a tip move the follower is drained without blocking.

Idle timeout: grapesy notices a gone client only when the handler sends to it, so a stream that has sent nothing for ten minutes ends with DEADLINE_EXCEEDED. A client that still wants the outcome reopens it.

Race contract: a transaction that reaches the chain between submission and this call is invisible - it is no longer in the mempool and will not appear in any block applied after the stream opens, so the stream never reports that ref. Clients must open WaitForTx before or concurrently with submitting the transaction.

Reconnect gap: for the same reason, a confirmation that lands between an idle close and the reopen is missed.

Rollbacks are not reported: a ref confirmed in a block that is later rolled back is not announced again; FollowTip's undo stream is the client-side tool for that.

Eviction is non-terminal: a ref that leaves the mempool without on-chain inclusion produces no message; the stream keeps waiting, since chain churn can legitimately re-add it later.

Mempool delivery follows observed membership: a ref gets STAGE_MEMPOOL when first observed in the mempool, and again after an observed removal and re-entry. Removal and re-entry between snapshots can be missed.

Duplicate refs in the request are treated as one. An empty request closes the stream immediately, with no messages sent - vacuously satisfied, and without opening a follower.

Throws INVALID_ARGUMENT if a ref is not a well-formed transaction id or the request has more than maxWaitForTxRefs refs, and DEADLINE_EXCEEDED when the idle timeout expires.
